 PUNTO d) INTERCEPTOR DE CARGA  (1 minuto)
==========================================================================

 QUÉ DECIR:
 "Un interceptor es una función que Angular ejecuta automáticamente en
  TODAS las peticiones que el frontend hace al backend. La registramos una
  sola vez en app.config.ts.

  Cuando el usuario presiona 'Ingresar', el método ingresar() primero valida
  que el usuario y la contraseña no estén vacíos. Luego llama al método
  login del AuthService, que prepara la petición al backend. Al suscribirnos,
  la petición sale y lo primero que hace es pasar por el interceptor de carga.

  Este interceptor llama a show() del LoadingService, que suma 1 a un
  contador de peticiones activas. Mientras ese contador sea mayor que cero,
  se muestra en pantalla el mensaje 'Cargando...'. Después, con next(req),
  deja que la petición continúe.

  Cuando llega la respuesta del servidor, haya salido bien o mal, se llama
  a hide(), que resta 1 al contador, y el 'Cargando...' desaparece.

  La ventaja es que ninguna pantalla tiene que acordarse de mostrar el
  'Cargando...': el interceptor lo hace solo."

 ARCHIVOS:
   interceptors/loading-interceptor.ts   -> show() al salir, hide() al volver
   services/loading.ts                   -> el contador
   app.html                              -> muestra el "Cargando..."

 MOSTRAR:
   F12 -> Network -> cambiar a "Slow 4G" -> iniciar sesión.
   Se ve el "Cargando..." con el círculo girando.
   (Luego volver a "No throttling".)

 PUNTO e) BEARER TOKEN INTERCEPTOR, TOAST Y LOCALSTORAGE  (2 minutos)
==========================================================================

 --- Bearer Token Interceptor ---
 QUÉ DECIR:
 "Después del interceptor de carga, la petición pasa por el Bearer Token
  Interceptor. Su trabajo es poner el token en cada petición.

  Como es el login, todavía no existe token, así que la deja pasar tal cual
  hacia el backend. El backend revisa el usuario y la contraseña y, si son
  correctos, devuelve un token: una especie de carnet que identifica al
  usuario."

 --- LocalStorage ---
 QUÉ DECIR:
 "Cuando el token llega, el AuthService lo guarda en el localStorage, que es
  una pequeña memoria del navegador. Por eso, si recargamos la página, la
  sesión se mantiene. Al cerrar sesión, el token se borra."

 --- De vuelta al Bearer Token Interceptor ---
 QUÉ DECIR:
 "A partir de ahí, en todas las peticiones siguientes, este interceptor lee
  el token del localStorage, hace una copia de la petición y le agrega la
  cabecera 'Authorization: Bearer' seguida del token. Authorization es el
  nombre estándar donde van las credenciales, y Bearer indica que es un
  token. Así el backend sabe quién hace cada petición, sin que ningún
  servicio tenga que poner el token manualmente.

  Además vigila las respuestas: si el backend responde 401 porque el token
  venció o fue alterado, cierra la sesión y lleva al login; si responde 403,
  avisa que el usuario no tiene permiso."

 --- Toast ---
 QUÉ DECIR:
 "Para avisar al usuario el resultado usamos toasts: mensajes cortos que
  aparecen en la esquina de la pantalla y desaparecen solos a los 3 segundos.
  Verde si salió bien, rojo si hubo un error, naranja para advertencias y
  azul para información.

  En el login, si todo sale bien, el toast muestra '¡Bienvenido!' y se va a
  la página principal. Si la contraseña es incorrecta, muestra el error en
  rojo."

 ARCHIVOS:
   interceptors/auth-interceptor.ts   -> pone el token, maneja 401 y 403
   services/storage.ts                -> guarda/lee/borra en localStorage
   services/auth.ts                   -> guarda el token al entrar, lo borra al salir
   services/toast.ts                  -> lista de mensajes
   components/toast-container/        -> los dibuja en pantalla

 MOSTRAR:
   1. Iniciar sesión con contraseña equivocada -> toast rojo.
   2. Iniciar sesión con jefe / jefe123        -> toast verde "¡Bienvenido!".
   3. F12 -> Application -> Local Storage      -> se ve "user_token".
   4. F12 -> Network -> abrir una petición de incidencias
      -> Request Headers -> "Authorization: Bearer eyJ...".
   5. Recargar la página (F5)                  -> sigue con la sesión.
   6. (Opcional) En Local Storage cambiar unas letras del token y abrir un
      módulo -> toast "Tu sesión ha caducado" y vuelve al login.

 PUNTO f) MENÚ SEGÚN EL PERFIL - CARGA DINÁMICA  (1 minuto y medio)
==========================================================================

 QUÉ DECIR:
 "El menú de la izquierda no está escrito en el código: se arma según el
  rol del usuario.

  En la base de datos tenemos la tabla de módulos y la tabla rol_modulo, que
  indica qué módulos puede ver cada rol. Cuando el usuario inicia sesión, el
  backend busca los módulos de su rol y los mete dentro del token.

  El frontend lee el token guardado en el localStorage y, con un @for, dibuja
  una opción por cada módulo. Por eso el jefe ve 4 opciones y el personal de
  sistemas ve solo 2.

  Además, si alguien intenta entrar escribiendo la dirección de un módulo que
  no le corresponde, un guard lo bloquea y muestra un aviso."

 ARCHIVOS:
   BD: tablas modulo y rol_modulo         -> qué ve cada rol
   components/principal/principal.html    -> el @for que dibuja el menú
   services/session.ts                    -> lee los módulos del token
   guards/modulo-guard.ts                 -> bloquea módulos ajenos

 MOSTRAR:

 SI ME PREGUNTAN...
==========================================================================

 ¿Qué es un interceptor?
   Una función que Angular ejecuta automáticamente en todas las peticiones
   HTTP, antes de enviarlas y cuando vuelve la respuesta.

 ¿Por qué un contador y no un true/false en el "Cargando..."?
   Porque puede haber varias peticiones a la vez (la pantalla de asignación
   hace 2). El "Cargando..." solo desaparece cuando terminan todas.

 ¿Por qué el login no lleva token?
   Porque el token se obtiene justamente al hacer login; todavía no existe.

 ¿Por qué "Authorization" y "Bearer"?
   Son nombres estándar de HTTP. Authorization es el campo de las
   credenciales y Bearer indica que es un token. El backend busca ese
   nombre exacto.

 ¿Por qué se hace una copia (clone) de la petición?
   Porque en Angular las peticiones no se pueden modificar; para agregarles
   algo se hace una copia con el cambio.

 ¿Qué pasa si el token vence?
   El backend responde 401, el interceptor borra el token, muestra un toast
   y lleva al login. El token dura 1 hora.

 ¿Por qué localStorage?
   Porque sus datos no se borran al recargar ni al cerrar el navegador,
   así la sesión se mantiene.

 ¿Dónde se decide qué módulos ve cada rol?
   En la tabla rol_modulo de la base de datos. Si se cambia ahí, el menú
   cambia sin tocar el código.
