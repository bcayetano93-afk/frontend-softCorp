   (base en memoria) porque todavía no existe el archivo .env.

 Lo que YA está listo en el backend:
   - src/main/resources/application.properties
       Lee la conexión desde el archivo .env
   - .env.example
       Plantilla con el formato de conexión de Neon
   - src/main/resources/schema.sql y data.sql
       Crean las tablas y cargan los datos solos al arrancar

 Pasos para completarlo:
   1. Entrar a https://neon.com, crear cuenta y un proyecto (ej. softcorp).
   2. En "Connect", desactivar "Connection pooling" y copiar los datos.
   3. Copiar .env.example como .env y completar:
        SPRING_DATASOURCE_URL=jdbc:postgresql://<host-de-neon>/neondb?sslmode=require
        SPRING_DATASOURCE_USERNAME=<usuario>
        SPRING_DATASOURCE_PASSWORD=<contraseña>
        TOKEN_JWT_SECRET=<clave generada con: openssl rand -base64 48>
   4. Arrancar el backend desde IntelliJ: las tablas se crean solas en Neon.

 En la exposición:

 c. SEGURIDAD: AUTENTICACIÓN, AUTORIZACIÓN, JWT, SEGURIDAD EN APIs [ OK ]
--------------------------------------------------------------------------

 AUTENTICACIÓN (quién eres) - Backend:
   - service/AuthService.java -> login(): compara la contraseña con BCrypt.
     Correcta: genera el token. Incorrecta: 401.
   - controller/AuthController.java -> POST /api/auth/login

 JWT (el token) - Backend:
   - service/JwtUtil.java
       Crea el token firmado con clave secreta. Dura 1 hora.
       Lleva: usuario, nombres, apellidos, rol y módulos.
   - security/JwtAuthenticationFilter.java
       En cada petición lee "Authorization: Bearer <token>", verifica firma
       y vencimiento, e identifica al usuario con su rol (ROLE_JEFE, etc.).

 AUTORIZACIÓN (qué puedes hacer) - Backend:
   - security/SecurityConfig.java
       /api/auth/**                      -> público
       PUT /api/v1/incidencias/*/asignar -> solo JEFE
       /api/v1/tecnicos/**               -> solo JEFE
       el resto                          -> cualquier usuario con token
     Sin token -> 401.  Con token pero sin el rol -> 403.

 SEGURIDAD EN APIs - Backend:
   - CORS: solo acepta peticiones de http://localhost:4200
   - Stateless: no guarda sesiones, cada petición trae su token
   - Contraseñas cifradas con BCrypt
   - Validación de datos (@NotBlank, @Pattern) -> 400 con mensaje claro
   - exception/GlobalExceptionHandler.java -> errores en JSON

 AUTORIZACIÓN - Frontend:
   - src/app/guards/auth-guard.ts   -> sin sesión no se entra a /principal
   - src/app/guards/modulo-guard.ts -> solo se entra a los módulos del rol,
                                       aunque se escriba la URL a mano

 En la exposición (Swagger: http://localhost:8080/swagger-ui/index.html):
   1. GET /api/v1/tecnicos/disponibilidad sin token        -> 401
   2. Login con sistemas, Authorize con su token, repetir  -> 403
   3. Login con jefe, Authorize con su token, repetir      -> 200
   4. En el frontend, con sistemas, escribir en la barra
      /principal/asignar-incidencia -> bloqueado con mensaje

 e. BEARER TOKEN INTERCEPTOR, TOAST, LOCALSTORAGE                  [ OK ]
--------------------------------------------------------------------------

 BEARER TOKEN INTERCEPTOR (Frontend):
   - src/app/interceptors/auth-interceptor.ts
       * Agrega "Authorization: Bearer <token>" a cada petición
         (por eso los servicios no escriben el token en ningún lado)
       * El login no lleva token
       * Si el backend responde 401: borra el token, muestra toast
         "Tu sesión ha caducado" y redirige al login
       * Si responde 403: toast "No tienes permiso..."

 TOAST (Frontend):
   - src/app/services/toast.ts                    -> lista de mensajes (se quitan a los 3 s)
   - src/app/components/toast-container/          -> los muestra arriba a la derecha
       verde = éxito, rojo = error, naranja = advertencia, azul = información
   Se usan en: login, registrar y asignar incidencia, cerrar sesión,
   sesión caducada y falta de permiso.

 LOCALSTORAGE (Frontend):
   - src/app/services/storage.ts  -> guardar / leer / borrar en localStorage
   - src/app/services/auth.ts     -> guarda el token al entrar, lo borra al salir
   - src/app/services/session.ts  -> decodifica el token: nombre, rol y módulos
   La sesión se mantiene aunque se recargue la página o se cierre el navegador.

 En la exposición:
   1. F12 -> Application -> Local Storage -> mostrar "user_token"
   2. F12 -> Network -> abrir una petición -> cabecera "Authorization: Bearer ..."
   3. Modificar el token en Local Storage y abrir un módulo
      -> toast "Tu sesión ha caducado" y regreso al login

   - src/app/components/principal/principal.ts   -> lee el usuario del token
   - src/app/app.routes.ts                       -> rutas hijas de /principal

 Cómo funciona:

        @for (modulo of user?.modulos; track modulo.url) {

        }
